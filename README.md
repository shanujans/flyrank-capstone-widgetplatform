# FlyRank Capstone — Embeddable Widget & Lead-Capture Platform

Let a customer configure a widget, hand them one line of `<script>`, and
safely catch everything the public internet throws back: validated,
spam-filtered, enriched, and dashboarded.

Stack: **Python + FastAPI + SQLite** (swappable to Postgres — see below).

## Architecture

```
Widget Owner (authenticated, Bearer JWT)
  -> Widget Management API -> Widget DB (tenant-isolated) -> embed snippet

Customer Website (any origin)
  <script src="/widget/v1/widget.js?id=123">
  -> GET /public/widgets/:id/config   (public · cached 60s · CORS: *)
  -> render widget in the page

Website Visitor
  -> POST /public/widgets/:id/submissions   (public · CORS: *)
     | body > 50KB?                -> 413
     | malformed / invalid JSON?   -> 422, clean JSON error
     | rate limit (IP, then widget)-> 429 + Retry-After if flooding
     | honeypot filled?            -> fake 201, nothing stored (spam)
     | required fields missing?    -> 422 with field names
     | geo enrich: Provider A -(down)-> Provider B -(down)-> store anyway
     | store submission
     | confirmation side effect (failure logged, NEVER blocks the response)
  <- 201 Created, submission (with geo if available)

Widget Owner
  -> Dashboard API <- submissions + stats (counts, per-day, geo breakdown)
```

Full design rationale (data model, layer sketch, the one explicit non-goal):
see [`DESIGN.md`](./DESIGN.md).

## Quick start (Docker — recommended, one command)

```bash
docker compose up --build
```

Then, in a second terminal, seed some demo data:

```bash
python scripts/seed.py http://localhost:8000
```

The seed script prints a demo login (email/password) and a widget id you can
use immediately.

## Quick start (without Docker)

```bash
python3 -m venv venv
source venv/bin/activate        # Windows: venv\Scripts\activate
pip install -r requirements.txt
cp .env.example .env            # defaults work out of the box (SQLite + mocked geo)
uvicorn app.main:app --reload
```

Then seed demo data the same way:

```bash
python scripts/seed.py http://localhost:8000
```

API docs (Swagger UI, auto-generated by FastAPI): http://localhost:8000/docs

## Seeing the widget actually render cross-origin

This is the part that matters most for this capstone: the widget rendering
on a page the platform doesn't control.

1. Start the API (above) and run the seed script — note the `embed snippet`
   it prints, and the widget id.
2. Open `customer-site/index.html`, replace `WIDGET_ID_HERE` in the
   `<script>` tag with your real widget id (and `127.0.0.1:8000` if your API
   runs elsewhere).
3. Serve that file from a **different port** than the API — this is what
   makes it a genuine cross-origin test, exactly like a real customer site:
   ```bash
   cd customer-site
   python -m http.server 5500
   ```
4. Open `http://127.0.0.1:5500/index.html` in a browser. The widget renders,
   and submitting it does a real cross-origin `fetch()` (preflight included)
   back to the API on port 8000.

## Proving the hardened behaviors manually (curl)

Register, log in, and create a widget:

```bash
curl -s -X POST localhost:8000/auth/register \
  -H 'Content-Type: application/json' \
  -d '{"email":"owner@example.com","password":"supersecret123"}'

TOKEN=$(curl -s -X POST localhost:8000/auth/login \
  -d 'username=owner@example.com&password=supersecret123' | python3 -c "import sys,json;print(json.load(sys.stdin)['access_token'])")

WIDGET_ID=$(curl -s -X POST localhost:8000/widgets -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"type":"signup_form","title":"Join us","fields":[{"name":"email","label":"Email","type":"email","required":true}]}' \
  | python3 -c "import sys,json;print(json.load(sys.stdin)['id'])")
```

**Force provider A down, prove fallback to B** (edit `.env`, set
`MOCK_GEO_PROVIDER_A_DOWN=true`, restart the server), then:

```bash
curl -s -X POST localhost:8000/public/widgets/$WIDGET_ID/submissions \
  -d '{"data":{"email":"x@example.com"},"hp_field":""}' | python3 -m json.tool
# "geo_provider": "provider_b"
```

**Force both down** (`MOCK_GEO_PROVIDER_B_DOWN=true` too) — the submission
still succeeds, just with `"geo_provider": null`.

**Force the notification side effect to fail** (`FORCE_NOTIFY_FAILURE=true`)
— the submission still returns `201` and is stored; only `"notified": false`
changes.

**Trip the honeypot** — fill `hp_field` like a bot would:

```bash
curl -s -X POST localhost:8000/public/widgets/$WIDGET_ID/submissions \
  -d '{"data":{"email":"bot@example.com"},"hp_field":"anything"}'
# looks like a normal 201 to the bot — nothing was actually stored
```

Full, real, unedited transcripts of every one of these (plus CORS preflight,
cache headers, tenant isolation, rate-limit bursts) are in
[`EVIDENCE.md`](./EVIDENCE.md) and [`tests/manual_evidence_transcript.txt`](./tests/manual_evidence_transcript.txt).

## Switching to Postgres

Nothing in the code is SQLite-specific — SQLAlchemy handles the dialect
difference. To switch:

1. In `docker-compose.yml`, uncomment the `db` service.
2. Add `psycopg2-binary` to `requirements.txt`.
3. Set `DATABASE_URL=postgresql+psycopg2://widget_user:widget_pass@db:5432/widget_platform`.

## Limitations (honest, on purpose)

- **Rate limiting is in-memory, single-process.** It resets on restart and
  doesn't share state across multiple workers/instances. Fine for this
  capstone's local scope; a real deployment would back it with Redis. See
  `DESIGN.md` §6 for the explicit non-goal writeup.
- **Auth is deliberately minimal** (email + bcrypt password + JWT, no
  refresh tokens, no password reset). Tenant isolation, not auth
  sophistication, is what this capstone is graded on.
- **Geo enrichment defaults to mocked** (`MOCK_GEO=true`) so the fallback
  chain is deterministic to test/grade. Set it `false` in `.env` to hit the
  real free providers (ip-api.com, ipapi.co) during manual exploration —
  note their free-tier rate limits (45 req/min and ~1,000/day respectively).
- **The widget UI is intentionally minimal** — a plain form, no CSS
  framework — per Section 7 of the brief ("the grade lives in the backend").
- **Email is a console log line**, not real SMTP, per the brief's $0 stack.
  What's graded is that its failure doesn't block the submission, not that
  mail is actually delivered.

## Project layout

```
app/
  main.py              FastAPI app, CORS, body-size guard, router wiring
  config.py            all settings, loaded from .env
  database.py          SQLAlchemy engine/session
  models.py            Tenant, Widget, Submission
  schemas.py           Pydantic request/response models + validation
  security.py          bcrypt hashing + JWT
  deps.py              auth dependency (resolves Bearer token -> Tenant)
  rate_limit.py         in-memory sliding-window limiter
  geo.py               IP -> geo enrichment with provider fallback chain
  notify.py            the safe confirmation side effect
  routers/
    auth.py            register / login
    widgets.py         authenticated CRUD + embed snippet, tenant-isolated
    public.py          widget.js, config, the hardened submission endpoint
    dashboard.py       authenticated analytics
  static/
    widget.v1.js       the actual embeddable script (vanilla JS)
customer-site/
  index.html           the "customer site" test page (different origin)
tests/
  conftest.py          isolated in-memory DB + fixtures per test
  test_capstone.py     17 tests covering all 6 acceptance probes
  manual_evidence_transcript.txt   real curl run against a live server
scripts/
  seed.py              demo tenant + widget + sample submissions
DESIGN.md              Phase 1 design doc
EVIDENCE.md            one proof per requirement checkbox
BUILDLOG.md            AI-usage log
capstone.yaml          evaluator manifest
```
